# Releases and Tags

This page documents how the Todoist Playbook is released, how Git tags are named, and how the three independent version axes in the repository relate to each other.

If anything here disagrees with the implementation, the implementation wins — update this page.

---

## The three version axes

The repository tracks versions in three different places, on purpose. They answer different questions.

| Axis | Where it lives | Format | Bumped by | Answers |
| --- | --- | --- | --- | --- |
| **Repository release tag** | Git tag + GitHub Release | `vYYYY.M.D` (with `-N` suffix on same-day re-runs) | `release.yml` → `reusable-release-assets.yml` | "What was published, and when?" |
| **Asset version** | `version:` in each `meta.yml` | SemVer `MAJOR.MINOR.PATCH` | `bump-template-version.yml` (auto) | "How mature is this template / prompt template?" |
| **Human changelog** | `CHANGELOG.md` | Keep-a-Changelog sections under `[Unreleased]` | Authors, in PRs | "What changed, in plain English?" |

Repository release tags are **calendar versions**, not SemVer. They identify a snapshot of the whole repository at a point in time. Individual asset SemVer is independent of the release tag and travels with each asset's `meta.yml`.

## Repository release tags

### Naming scheme

Tags use **CalVer**: `vYYYY.M.D` in UTC.

- `v2026.4.27` — first release on 27 April 2026
- `v2026.4.27-2` — second release the same day
- `v2026.4.27-3` — third release the same day, etc.

The tag computation lives in [reusable-release-assets.yml](../.github/workflows/reusable-release-assets.yml):

1. Compute `BASE_TAG = vYYYY.M.D` from `datetime.now(timezone.utc)`.
2. Probe `refs/tags/<BASE_TAG>` on `origin`. If it exists, append `-2`, `-3`, … until a free name is found.
3. Use that as the release tag.

There is intentionally no leading-zero padding (`v2026.4.7`, not `v2026.04.07`), to match what the workflow produces.

### What ships in a release

Every release attaches three assets, all generated by [generate_release_assets.py](../.github/scripts/generate_release_assets.py):

- `csv-templates.zip` — every CSV template folder
- `prompt-templates.zip` — every prompt template folder
- `index.json` — machine-readable catalogue of templates, prompt templates, and bundles

Release notes are produced by `gh release create … --generate-notes`, which uses the squash commit subjects since the previous tag (Conventional Commits style — see [CONTRIBUTING](../CONTRIBUTING)).

### When a release fires

[release.yml](../.github/workflows/release.yml) runs on:

1. **`workflow_run`** — after the `Validate templates` workflow completes successfully on a `push` to `main`. The release job only runs if `workflow_run.conclusion == 'success'` and `workflow_run.event == 'push'`. PR-triggered validations do not produce releases.
2. **`workflow_dispatch`** — manual run from the Actions tab, e.g. to re-publish if a release was deleted or to ship a docs-only sweep.

Concurrency is keyed on `github.workflow`-`github.ref` with `cancel-in-progress: false`, so two releases for `main` queue rather than racing.

### Permissions

`release.yml` declares `permissions: {}` at the top level and grants `contents: write` only on the `release` job. The reusable workflow does the same. Nothing else is granted.

## Asset SemVer (per template / prompt template)

Each CSV template and prompt template carries its own SemVer in `meta.yml`. This version is **decoupled** from repository release tags.

| `version:` value | Meaning |
| --- | --- |
| `0.0.0` | Unreviewed. Treated as draft; surfaced as a `to-be-reviewed` issue by `sync-template-review-issues.yml`. |
| `0.1.0` | Reviewed and stable — the first "real" published version. |
| `0.1.x` and onward | Patch-level changes auto-bumped by [bump-template-version.yml](../.github/workflows/bump-template-version.yml) when the asset's files change in a merged PR. |
| `0.x.0` / `1.0.0+` | Reserved for breaking schema or content reorganisations. Bump by hand in a PR. |

**Do not hand-bump patch versions.** The bump workflow detects which assets a merged PR touched and bumps each affected `meta.yml` patch level in a follow-up commit on `main`. Hand-bumping causes drift.

The graduation step from `0.0.0` → `0.1.0` is intentional and manual — it is the asset-review checkpoint, performed via the `review-unreviewed-asset` skill or the `Template Reviewer` agent.

## CHANGELOG

[CHANGELOG.md](../CHANGELOG.md) follows the Keep-a-Changelog convention with an `[Unreleased]` section accumulating entries between releases.

- Every PR that adds, changes, removes, deprecates, or fixes user-visible behaviour adds a bullet under the appropriate subsection of `[Unreleased]` (`### Added`, `### Changed`, `### Removed`, `### Deprecated`, `### Fixed`).
- Internal-only refactors that have no user-visible effect may skip the changelog.
- Release tags themselves do **not** currently rotate `[Unreleased]` into a dated section — release notes are generated from commit history by `gh release create --generate-notes`. The `[Unreleased]` section is allowed to accumulate across multiple releases until a manual cut.

If we move to per-release CHANGELOG sections later, the convention will be: when cutting a release, rename `[Unreleased]` to `[vYYYY.M.D] - YYYY-MM-DD`, then add a fresh empty `[Unreleased]` above it.

## Bundles

Bundles (`bundles/{slug}/bundle.yml`) reference CSV templates and prompt templates by slug. They do **not** carry their own SemVer — they pin the current set of slugs and rely on each member asset's own version. A bundle changes when its `bundle.yml` changes, and that change rides in the next repository release.

---

## Re-running a release

Manual release re-run from the Actions tab:

1. Go to **Actions → Publish Release → Run workflow** on `main`.
2. The reusable workflow regenerates assets, computes the next free tag for today, and creates a fresh GitHub Release.

This is the supported path. Do not push tags by hand — the tag name is computed by the workflow and a hand-pushed tag will collide.
